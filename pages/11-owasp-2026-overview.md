# 11. OWASP LLM Top 10 2026 개요

OWASP GenAI Security Project는 2026년 8월 LLM 애플리케이션용 Top 10의 2026년판을 발표했다. 이 판의 가장 큰 특징은 순위 결정 방식이다. 처음으로 커뮤니티 투표에 실제 사고 사례 코퍼스를 가중했다. 즉, 순위가 전문가의 직감이 아니라 실제 발생한 사고 기록을 반영하기 시작했다는 뜻이다. 10장에서도 말했듯이, 이것은 순위표 자체가 위협 지형의 변화를 읽는 도구가 됐다는 의미다. 전체 목록과 설명은 공식 사이트 https://genai.owasp.org/ 에서 확인할 수 있다.

## 10개 항목 일람

LLM01 Prompt Injection(프롬프트 인젝션). 공격자가 악성 입력을 심어 모델의 행동을 조작하는 공격이다. 직접 인젝션(사용자 입력에 지시 숨기기)과 간접 인젝션(문서·웹 페이지·도구 결과에 지시 숨기기)이 있다. 2025년판에 이어 1위를 지켰다. 에이전트 시대에도 가장 기본이면서 가장 빈번한 공격이다. 이 책의 20장에서 실전 방어와 함께 다룬다.

LLM02 Sensitive Information Disclosure(민감 정보 노출). 모델이 학습 데이터나 컨텍스트에 있던 민감 정보를 응답에 노출하는 문제다. 개인정보, API 키, 사내 문서 내용이 대표적인 사례다. 2025년판에 이어 2위를 지켰다. RAG와 에이전트가 보편화되면서 컨텍스트에 들어가는 민감 정보의 양이 늘어나고 있다. 21장에서 다룬다.

LLM03 Excessive Agency(과도한 에이전시). LLM 앱(특히 에이전트)에게 필요 이상의 권한, 기능, 자율성을 부여한 상태다. 도구가 너무 많거나, 민감한 도구에 대한 제한이 없거나, 사람의 승인 없이 파괴적인 행동을 할 수 있을 때 발생한다. 2025년판 6위에서 2026년판 3위로 급등했다. 에이전트 시대의 사고 기록이 순위에 그대로 반영된 결과다. 22장에서 다룬다.

LLM04 Supply Chain(공급망). 모델, 데이터셋, 플러그인, MCP 서버, 임베딩 서비스, 서드파티 라이브러리 같은 구성 요소에서 발생하는 위험이다. 오염된 사전 학습 모델이나 악성 플러그인이 대표적이다. 2025년판 3위에서 2026년판 4위로 한 계단 내려갔다. 23장에서 다룬다.

LLM05 Data and Model Poisoning(데이터·모델 포이즈닝). 학습 데이터, 파인튜닝 데이터, 임베딩 데이터를 오염시켜 모델의 행동을 왜곡하는 공격이다. 백도어나 편향 주입이 대표적인 기법이다. 2025년판 4위에서 2026년판 5위로 한 계단 내려갔다. 24장에서 다룬다.

LLM06 Unbounded Consumption(무제한 소비). 요청·토큰·추론 비용에 제한이 없어 발생하는 위험이다. 자동화된 요청 폭주로 API 비용이 폭증하거나 서비스가 마비될 수 있다. 2025년판 10위에서 2026년판 6위로 네 계단 상승했다. 고비용 추론 모델이 보편화되면서 보안 문제가 곧 비용 문제가 됐다. 25장에서 다룬다.

LLM07 Misinformation(허위정보). 모델이 그럴듯하지만 틀린 정보를 사실처럼 생성하는 문제다. 환각(hallucination)이 대표적이며, 의료·법률·금융처럼 정확성이 중요한 분야에서 피해가 크다. 2025년판 9위에서 2026년판 7위로 두 계단 상승했다. 26장에서 다룬다.

LLM08 Hidden Context Exposure(숨겨진 컨텍스트 노출). 2025년판의 System Prompt Leakage(시스템 프롬프트 유출)에서 이름이 바뀌고 범위가 확장된 항목이다. 시스템 프롬프트뿐 아니라 내부 정책 로직, 도구 정의, 비밀값, 컨텍스트 구성 같은 숨겨진 컨텍스트 전체의 노출을 포괄한다. 2025년판 7위에서 2026년판 8위다. 27장에서 다룬다.

LLM09 Vector and Embedding Weaknesses(벡터·임베딩 취약점). 벡터 데이터베이스와 임베딩 파이프라인의 취약점이다. 임베딩 반전으로 원문을 복원하거나, 벡터 DB에 악성 문서를 주입하는 공격이 해당한다. 2025년판 8위에서 2026년판 9위로 한 계단 내려갔다. 28장에서 다룬다.

LLM10 Improper Output Handling(부적절한 출력 처리). 모델의 출력을 검증 없이 하류 시스템에 전달할 때 발생하는 문제다. 출력에 포함된 자바스크립트가 브라우저에서 실행되거나, SQL 인젝션 페이로드가 그대로 DB에 전달되는 식이다. 2025년판 5위에서 2026년판 10위로 다섯 계단 하락했다. 중요도가 낮아진 것이 아니라 다른 항목의 사고가 더 빠르게 늘어난 결과로 읽힌다. 29장에서 다룬다.

## 주요 신호 3가지

순위표에서 읽어야 할 신호는 세 가지다.

첫째, 과도한 에이전시의 급등이다. LLM03이 6위에서 3위로 세 계단 올랐다. OWASP가 2026년판 순위를 실제 사고 사례 코퍼스에 가중해 결정했다는 점을 감안하면, 이 상승은 이론이 아니라 기록이다. 에이전트가 도구를 들고 행동하기 시작하면서 손실이 자율성에 집중되고 있다. 에이전트를 만들거나 운영하는 개발자에게 이 항목은 최우선순위다.

둘째, 무제한 소비의 상승이다. LLM06이 10위에서 6위로 네 계단 올랐다. 추론 비용이 높은 모델이 보편화되면서, 자동화된 요청 폭주는 곧바로 돈의 손실로 이어진다. 비용 제한(rate limit, 할당량, 예산 알림)은 이제 비용 관리가 아니라 보안 통제다. 25장에서 구체적인 방어 구현을 다룬다.

셋째, 부적절한 출력 처리의 하락이다. LLM10이 5위에서 10위로 다섯 계단 내려갔다. 그렇다고 출력 검증이 중요하지 않아진 것은 아니다. 출력 처리는 여전히 기본 방어선이며, 29장과 Part 3의 30장에서 계속 다룬다. 하락은 다른 항목들의 사고가 더 빠르게 늘어났다는 의미로 읽는 것이 맞다. 기본기가 약해졌다는 신호로 오해하면 안 된다.

여기에 하나를 더 덧붙이자면, LLM08의 개명과 확장이다. 구 명칭 System Prompt Leakage에서 Hidden Context Exposure로 바뀌면서, 시스템 프롬프트뿐 아니라 정책 로직, 도구 정의, 비밀값 등 숨겨진 컨텍스트 전체를 포괄하게 됐다. 방어해야 할 대상이 넓어진 만큼, 27장에서 다루는 대응 범위도 넓어졌다.

## 이 책에서 이 목록을 쓰는 법

이 책의 Part 2는 이 10개 항목을 순서대로 한 장씩 다룬다. 20장부터 29장까지, 각 장은 공격 방식, 실제 영향, 방어 구현의 순서로 구성된다. 순위가 높다고 해서 먼저 읽을 필요는 없다. 지금 만들고 있는 앱의 구조에 가장 가까운 장부터 읽어도 된다.

다만 10장의 그림을 다시 떠올려보자. 공격 표면은 다섯 개 지점으로 넓어져 있다. 10개 항목은 그 넓어진 표면을 항목별로 자른 것이다. 항목을 따로따로 막는 것도 중요하지만, 12장에서 배울 위협 모델링으로 전체 그림을 먼저 그려두면 각 방어의 위치가 훨씬 명확해진다.

## 코드로 보는 2026년판 목록

10개 항목을 코드로 정리해두면 Part 2를 읽을 때 빠르게 참조할 수 있다. 아래는 2026년판 목록과 2025년판 대비 변화를 담은 간단한 스크립트다.

```python
# owasp_2026.py - OWASP LLM Top 10 2026 요약 참조 스크립트
items = [
    ("LLM01", "Prompt Injection", "프롬프트 인젝션", 1, 1),
    ("LLM02", "Sensitive Information Disclosure", "민감 정보 노출", 2, 2),
    ("LLM03", "Excessive Agency", "과도한 에이전시", 3, 6),
    ("LLM04", "Supply Chain", "공급망", 4, 3),
    ("LLM05", "Data and Model Poisoning", "데이터·모델 포이즈닝", 5, 4),
    ("LLM06", "Unbounded Consumption", "무제한 소비", 6, 10),
    ("LLM07", "Misinformation", "허위정보", 7, 9),
    ("LLM08", "Hidden Context Exposure", "히든 컨텍스트 노출", 8, 7),
    ("LLM09", "Vector and Embedding Weaknesses", "벡터·임베딩 취약점", 9, 8),
    ("LLM10", "Improper Output Handling", "부적절한 출력 처리", 10, 5),
]

for code, en, ko, rank26, rank25 in items:
    diff = rank25 - rank26
    if diff > 0:
        change = "상승 " + str(diff) + "계단"
    elif diff < 0:
        change = "하락 " + str(abs(diff)) + "계단"
    else:
        change = "유지"
    print(code, ko + " (" + en + ")", "2026년 " + str(rank26) + "위", "->", change)
```

실행하면 10개 항목의 순위와 변화가 한눈에 출력된다. 이 스크립트를 저장소의 참조 자료로 두고, Part 2의 각 장을 읽을 때마다 해당 항목의 순위를 확인해보자.

## 내 앱에 적용하는 우선순위 정하기

순위표는 전체 업계의 평균적인 위험 순위다. 내 앱의 우선순위는 앱의 구조에 따라 달라진다. 아래 질문에 답해보자.

- 에이전트가 도구를 쓰는가? 예라면 LLM03(과도한 에이전시), LLM01(프롬프트 인젝션)이 최우선이다. 도구가 곧 공격자의 손발이 되기 때문이다.
- RAG로 외부 문서를 읽는가? 예라면 LLM01의 간접 인젝션, LLM08(히든 컨텍스트 노출), LLM09(벡터·임베딩 취약점)를 먼저 본다.
- API 비용이 걱정되는가? LLM06(무제한 소비)의 25장을 먼저 읽는다. 비용 제한은 구현이 비교적 간단하면서 효과가 확실한 방어다.
- 모델 출력을 그대로 웹에 보여주거나 DB에 저장하는가? LLM10(부적절한 출력 처리)의 29장과 Part 3의 30장이 우선이다.
- 서드파티 플러그인이나 MCP 서버를 쓰는가? LLM04(공급망)의 23장과 42장을 먼저 본다.

이 질문들에 대한 답을 12장의 위협 모델링 결과와 함께 적어두자. 그러면 "우리 팀이 이번 분기에 막아야 할 것"의 목록이 자연스럽게 나온다.

## 순위표를 대하는 태도

마지막으로 한 가지 당부다. 순위표는 지도이지 목적지가 아니다. 1위인 프롬프트 인젝션만 막고 끝내는 것이 목표가 아니라, 10개 항목을 전부 훑으며 자신의 앱에 해당하는 위험을 찾는 것이 목표다. 특히 순위가 하락한 항목을 무시하지 말자. LLM10의 하락은 출력 검증이 쉬워졌다는 뜻이 아니라, 다른 위험이 더 빠르게 커졌다는 뜻이다. 기본기는 순위에 상관없이 지켜야 한다.

다음 12장에서는 이 10개 항목을 자신의 앱에 대입하는 방법, 즉 위협 모델링의 기초를 배운다.

## 2026년판이 말하는 시대 변화

순위 변화를 한 문장으로 요약하면 이렇다. "모델이 말하는 시대의 위험에서, 모델이 행동하는 시대의 위험으로."

상위권을 지킨 LLM01과 LLM02는 변하지 않는 기본기다. 프롬프트 인젝션과 민감 정보 노출은 LLM 앱이 존재하는 한 계속 1, 2위를 다툴 것이다. 이 두 항목이 유지됐다는 것은, 새로운 위험이 추가된 것이지 기존 위험이 사라진 것이 아니라는 뜻이다.

3위로 급등한 LLM03은 시대의 변화를 가장 직접적으로 보여준다. 에이전트가 보편화되면서 "모델이 무슨 말을 하는가"보다 "모델이 무슨 행동을 하는가"가 더 큰 손실로 이어지기 시작했다. OWASP가 2026년판 순위를 실제 사고 사례 코퍼스에 가중해 결정했다는 점을 다시 떠올려보자. 이 상승은 설문 응답자의 인상 투표가 아니라 사고 기록이 만든 순위다.

6위로 올라온 LLM06은 보안과 비용의 경계가 무너졌음을 보여준다. 예전에는 보안 사고와 비용 사고가 다른 팀의 일이었다. 이제는 무제한 소비가 곧 보안 사고다. 비용 제한을 거는 것은 FinOps의 일이 아니라 보안 통제의 일이다.

10위로 내려간 LLM10에 대해서는 오해를 경계해야 한다. 순위가 내려갔다고 해서 출력 검증을 건너뛰어도 된다는 뜻이 아니다. 출력 처리는 다른 모든 방어의 마지막 보루다. 입력 검증을 뚫고 들어온 공격도, 출력 단계에서 한 번 더 걸러낼 수 있다. 29장과 30장에서 이 마지막 보루를 어떻게 쌓는지 다룬다.

## 이 목록의 한계

OWASP Top 10을 공부할 때 한계도 함께 알아두자.

첫째, 이 목록은 웹 애플리케이션 중심의 관점에서 작성됐다. 임베디드 기기나 특수 환경의 LLM 활용에서는 다른 위험이 더 클 수 있다. 자신의 환경에 맞게 조정해서 쓰자.

둘째, 순위는 상대적이다. 10위라고 해서 무시해도 되는 항목이 아니다. 자신의 앱 구조에 따라 10위 항목이 가장 치명적일 수 있다. 12장의 위협 모델링으로 자신의 우선순위를 따로 정하는 이유다.

셋째, 목록은 공격 기법의 카탈로그가 아니다. "이런 종류의 위험이 있다"는 분류 체계지, "이렇게 공격한다"는 매뉴얼이 아니다. 구체적인 공격 기법과 방어 코드는 이 책의 Part 2 각 장에서 다룬다.
