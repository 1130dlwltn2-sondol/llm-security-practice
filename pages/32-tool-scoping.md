# 32. 최소 권한 도구 스코핑

에이전트에게 도구를 주는 것은 직원에게 열쇠를 주는 것과 같다. 모든 방의 열쇠를 줄 수도 있고, 필요한 방의 열쇠만 줄 수도 있다. 최소 권한 도구 스코핑은 후자를 설계하는 일이다. 에이전트에게 주는 도구를 기능, 권한, 범위 기준으로 좁혀서, 에이전트가 할 수 있는 일의 상한을 미리 정해 두는 것이다.

이 장의 원칙은 전통 보안의 최소 권한 원칙(least privilege)을 에이전트에 적용한 것이다. 에이전트가 똑똑해질수록 도구를 많이 주고 싶어지지만, 도구가 많아질수록 공격 표면도 넓어진다. 27장에서 다룬 도구 목록 노출 제한이 '보여주는 것'의 문제였다면, 이 장은 '실제로 쥐여주는 것'의 문제다.

## 32.1 왜 도구를 좁혀야 하는가

에이전트의 능력은 도구가 정한다. 모델 자체는 텍스트만 내놓을 뿐, 실제로 세상에 영향을 주는 것은 도구 호출이다. 파일 읽기, DB 조회, 이메일 발송, 코드 실행 같은 도구가 에이전트의 손과 발이다.

문제는 에이전트의 판단이 완벽하지 않다는 것이다. 프롬프트 인젝션으로 속을 수도 있고, 할루시네이션으로 엉뚱한 인자를 넣을 수도 있다. 에이전트가 실수하거나 속았을 때 피해를 제한하는 가장 확실한 방법은, 애초에 위험한 도구를 주지 않거나 위험한 범위를 잘라내는 것이다. 사후 대응보다 사전 제한이 항상 싸다.

예를 들어보자. 고객 문의를 처리하는 에이전트에게 '주문 조회'와 '환불 처리' 도구가 필요하다고 하자. 그런데 환불 처리 도구가 금액 제한 없이 전체 주문을 환불할 수 있게 설계되어 있다면, 에이전트의 한 번의 실수가 전액 환불 사고로 이어진다. 도구를 줄 때부터 "10만 원 이하의 주문만, 당일 주문만" 같은 범위를 박아 두면 사고의 크기가 제한된다.

## 32.2 읽기 전용과 쓰기 도구의 분리

첫 번째 설계 원칙은 읽기 도구와 쓰기 도구를 분리하는 것이다. 읽기는 대체로 안전하고, 쓰기는 위험하다. 이 둘을 같은 권한으로 묶지 않는다.

실무 적용은 세 가지다.

첫째, 도구 자체를 나눈다. search_orders(조회용)와 refund_order(처리용)를 별도 도구로 정의하고, 각각 다른 권한으로 실행되게 한다. 조회용 도구는 읽기 전용 DB 계정으로, 처리용 도구는 별도 승인을 거치는 계정으로 동작하게 한다.

둘째, 에이전트의 역할에 따라 도구 구성을 다르게 한다. 1차 상담 에이전트에게는 조회 도구만 주고, 환불 같은 쓰기 작업은 별도 에이전트나 사람 승인(33장)을 거치게 한다.

셋째, 쓰기 도구의 실행은 항상 로그를 남긴다. 누가(어떤 에이전트 세션), 언제, 무엇을 바꿨는지를 기록한다. 31장에서 다룬 감사 로그와 같은 맥락이다.

여기에 한 겹을 더하면, 도구 호출 직전에 권한을 다시 확인하는 것이다. 에이전트 생성 시점에 도구를 제한했더라도, 호출 시점에 한 번 더 검사하면 설정 실수로 인한 권한 누출을 막을 수 있다.

```python
def call_tool(role: str, tool_name: str, args: dict) -> dict:
    # 호출 직전 권한 재확인 (방어의 겹침)
    if not can_call(role, tool_name):
        return {"ok": False, "error": f"역할 {role}에 허용되지 않은 도구: {tool_name}"}
    spec = TOOLS[tool_name]
    if spec.get("requires_approval"):
        return {"ok": False, "error": "사람 승인이 필요합니다. 승인 후 다시 호출하세요."}
    return execute_tool(spec, args)
```

생성 시점의 제한과 호출 시점의 검사가 서로 다른 버그를 잡는다. 생성 시점 제한은 설계 실수를, 호출 시점 검사는 설정 변경이나 코드 변경으로 인한 누락을 잡는다.

```python
# 도구 정의 예시: 읽기/쓰기 분리
TOOLS = {
    "search_orders": {
        "kind": "read",
        "db_role": "report_reader",  # 읽기 전용 계정
        "description": "주문 번호로 주문 정보를 조회한다.",
    },
    "refund_order": {
        "kind": "write",
        "db_role": "refund_writer",  # 쓰기 계정. 별도 승인 필요
        "requires_approval": True,   # 33장의 사람 승인과 연결
        "description": "주문을 환불 처리한다. 사람 승인이 필요하다.",
    },
}
```

kind 필드 하나로 도구의 성격이 명확해진다. 에이전트에게 보여주는 설명에는 권한 얘기를 자세히 적지 않되(27장의 노출 제한), 서버 측에서는 kind에 따라 실행 경로를 엄격히 분리한다.

## 32.3 위험 액션의 스코프 한정

두 번째 원칙은 위험한 액션의 범위를 좁히는 것이다. 도구를 주되, "어디까지" 할 수 있는지를 제한한다.

대표적인 예가 파일 삭제다. 에이전트에게 파일 정리 작업을 맡긴다면, 삭제 가능한 디렉터리를 하나로 한정한다. /tmp/work 같은 작업 디렉터리만 지울 수 있고, 그 밖은 건드리지 못하게 한다.

```python
import os

ALLOWED_DELETE_DIR = "/tmp/agent-work"

def safe_delete(path: str) -> dict:
    # 경로 정규화 후 허용된 디렉터리 안인지 확인
    real = os.path.realpath(path)
    allowed = os.path.realpath(ALLOWED_DELETE_DIR)
    if not real.startswith(allowed + os.sep):
        return {"ok": False, "error": "허용된 디렉터리 밖의 삭제는 금지됩니다."}
    if real == allowed:
        return {"ok": False, "error": "작업 디렉터리 자체는 삭제할 수 없습니다."}
    os.remove(real)
    return {"ok": True}

print(safe_delete("/tmp/agent-work/old.txt"))
print(safe_delete("/etc/passwd"))
```

realpath로 정규화하는 것이 포인트다. ".." 이나 심볼릭 링크로 허용 디렉터리를 벗어나는 우회를 막는다. 경로 검사는 문자열 비교가 아니라 정규화된 실제 경로로 해야 한다.

DB 작업도 마찬가지다. 업데이트 가능한 테이블을 허용 목록으로 정하고, WHERE 절 없는 전체 업데이트를 금지하는 식이다. 네트워크 호출은 허용된 도메인 목록으로 제한한다. Claude Code의 네트워크 이그레스 허용 목록이 바로 이 원칙의 실제 구현이다.

## 32.4 토큰 스코프 최소화

세 번째 원칙은 도구가 쓰는 자격 증명 자체의 권한을 줄이는 것이다. 에이전트가 호출하는 외부 API의 토큰이 관리자급 권한을 들고 있다면, 에이전트가 탈취되거나 오작동할 때 피해가 토큰의 권한만큼 커진다.

원칙은 단순하다. 토큰에는 그 도구가 실제로 하는 일에 필요한 최소 권한만 부여한다. 조회용 도구의 토큰에는 읽기 스코프만, 특정 저장소에만 접근하는 도구의 토큰에는 해당 저장소 스코프만 준다.

```python
# 나쁜 예: 만능 토큰을 모든 도구가 공유
SHARED_TOKEN = "sk-dummy-0000"  # admin 스코프. 어디서든 유출되면 전체 장악

# 좋은 예: 용도별 최소 스코프 토큰
TOKENS = {
    "search_orders": "sk-dummy-1111",  # orders:read 스코프만
    "send_notice": "sk-dummy-2222",    # notice:send 스코프만
}
```

토큰을 나누면 관리가 번거로워지지만, 사고 시 피해 범위가 토큰 단위로 격리된다. 토큰은 환경변수나 시크릿 매니저에서 주입하고, 코드나 프롬프트에 하드코딩하지 않는다(27장 원칙과 동일).

## 32.5 에이전트 역할별 도구 매트릭스

도구 스코핑을 설계할 때 유용한 도구가 역할별 도구 매트릭스다. 행에 에이전트 역할, 열에 도구를 놓고, 각 칸에 허용 여부를 적는 표다. 표를 그리면 과도한 권한이 눈에 보인다.

예시:

| 역할 / 도구 | 주문 조회 | 배송지 변경 | 환불 처리 | DB 직접 조회 |
| 1차 상담 에이전트 | 허용 | 거부 | 거부 | 거부 |
| 환불 전담 에이전트 | 허용 | 허용 | 승인 후 허용 | 거부 |
| 관리자 에이전트 | 허용 | 허용 | 승인 후 허용 | 읽기 전용 |

이 표를 코드로 옮기면 정책이 된다.

```python
TOOL_MATRIX = {
    "support_agent": {"search_orders", "track_delivery"},
    "refund_agent": {"search_orders", "track_delivery", "refund_order"},
    "admin_agent": {"search_orders", "track_delivery", "refund_order", "db_readonly"},
}

def allowed_tools(role: str) -> set:
    return TOOL_MATRIX.get(role, set())

def can_call(role: str, tool: str) -> bool:
    return tool in allowed_tools(role)

# 에이전트 생성 시 역할에 맞는 도구만 주입
def build_agent(role: str):
    tools = {name: TOOLS[name] for name in allowed_tools(role)}
    return {"role": role, "tools": tools}
```

매트릭스의 관리 원칙은 두 가지다. 첫째, 새 도구가 생기면 매트릭스에 먼저 반영하고 기본값은 거부다. 허용을 기본값으로 두면 새 도구가 모든 역할에 열려 버린다. 둘째, 분기별로 리뷰한다. 역할이 바뀌거나 도구가 추가되면서 매트릭스가 현실과 어긋나기 때문이다. 리뷰할 때는 "이 역할이 이 도구를 실제로 쓴 기록이 있는가"를 감사 로그로 확인한다. 쓰지 않는 권한은 회수한다.

한 가지 덧붙이자. 매트릭스는 에이전트에게 보여주지 않는다. 에이전트는 자신에게 주어진 도구만 알면 된다. "네게는 이 도구가 금지되어 있다"는 정보 자체가 공격자에게는 시스템 구조 정보다. 27장의 도구 목록 노출 제한과 같은 원칙이다. 관리는 서버 측에서, 에이전트에게는 최소한만 보여준다.

## 32.6 실습: 도구 권한 리뷰

이번 장의 실습은 주어진 도구 정의 목록을 검토하고 과도한 권한을 찾아 줄이는 리뷰 실습이다. 실제 보안 리뷰에서 하는 일을 축소한 형태로, 로컬에서 안전하게 따라 할 수 있다.

목표: 아래 도구 정의 목록에서 과도한 권한 4가지를 찾아내고, 수정된 정의를 작성한다.

1. 새 텍스트 파일에 아래 '리뷰 대상' 도구 정의를 복사한다.

```json
{
  "tools": [
    {
      "name": "db_query",
      "description": "DB에 임의의 SQL을 실행한다.",
      "db_role": "db_admin"
    },
    {
      "name": "file_manager",
      "description": "파일을 읽고 쓰고 삭제한다. 전체 파일 시스템 접근 가능.",
      "allowed_dir": "/"
    },
    {
      "name": "send_email",
      "description": "고객에게 이메일을 발송한다.",
      "token_scope": "mail:send, mail:read, admin"
    },
    {
      "name": "web_fetch",
      "description": "URL의 내용을 가져온다.",
      "allowed_domains": ["*"]
    }
  ]
}
```

2. 각 도구의 문제점을 적어 본다. 힌트:
   - db_query: 임의 SQL + 관리자 계정은 29장의 부적절한 출력 처리와 직결된다. 읽기 전용 계정과 허용된 쿼리 형태로 바꿀 수 없을지 검토한다.
   - file_manager: 전체 파일 시스템 접근은 32.3절의 스코프 한정 원칙에 어긋난다. 읽기/쓰기/삭제를 분리하고 디렉터리를 한정한다.
   - send_email: 발송 도구에 읽기 권한과 admin 스코프가 섞여 있다. 발송에 필요한 최소 스코프만 남긴다.
   - web_fetch: 모든 도메인 허용은 SSRF(서버 측 요청 위조)의 여지를 준다. 필요한 도메인만 허용 목록에 넣는다.
3. 수정된 도구 정의를 JSON으로 작성한다. 각 수정에 "왜 이렇게 바꿨는지" 한 줄 설명을 덧붙인다.
4. 스스로 채점한다. 네 가지 문제점을 모두 찾고, 수정안이 32.2~32.4절의 원칙(읽기/쓰기 분리, 스코프 한정, 토큰 최소화)에 맞으면 완성이다.
5. 완성된 매트릭스를 32.5절의 TOOL_MATRIX 형태로 옮겨 보고, can_call 함수로 각 역할의 호출 가능 여부를 테스트한다. 표로 그린 정책이 코드로 동작하는 것을 확인하는 것이 마지막 단계다.

이 실습의 핵심은 '에이전트에게 도구를 줄 때 기본값은 의심'이라는 태도다. 편리하다는 이유로 넓게 준 권한은 사고가 터진 뒤에야 비싸게 느껴진다. 매트릭스로 그리고, 코드로 강제하고, 주기적으로 리뷰하라.

## 32.7 정리

- 에이전트의 능력은 도구가 정한다. 에이전트의 실수나 오작동에 대비해 도구의 권한을 미리 좁혀 둔다.
- 읽기 도구와 쓰기 도구를 분리한다. 쓰기 도구는 별도 권한과 로깅, 필요하면 사람 승인을 붙인다.
- 위험 액션은 범위를 한정한다. 파일 삭제는 특정 디렉터리로, DB 쓰기는 허용 테이블로, 네트워크는 허용 도메인으로.
- 토큰은 용도별 최소 스코프로 나눈다. 만능 토큰 하나가 모든 도구의 단일 실패 지점이 되지 않게 한다.
- 새 도구는 기본 거부로 매트릭스에 등록하고, 분기별로 실제 사용 기록과 대조해 리뷰한다.
- Claude Code의 네트워크 이그레스 허용 목록처럼, 스코핑은 실제 제품에서도 쓰이는 기본기다.
