# 12. LLM 앱 위협 모델링 기초

위협 모델링은 "우리 시스템이 어디서 어떻게 뚫릴 수 있는가"를 미리 그려보는 작업이다. 거창한 방법론이 아니다. 종이에 상자를 그리고, 화살표를 긋고, "여기서 공격자가 뭘 할 수 있지?"라고 묻는 것이 전부다. 이 장에서는 LLM 앱에 맞게 단순화한 세 단계, 즉 신뢰 경계, 공격 표면, 자산 식별을 배운다. 그리고 간단한 채팅봇 예제로 직접 실습한다.

## 신뢰 경계: 믿을 것과 믿지 못할 것

신뢰 경계(trust boundary)는 데이터를 믿을 수 있는 영역과 믿을 수 없는 영역을 나누는 선이다. LLM 앱에서는 이 선을 긋는 것이 전통적인 앱보다 어렵다. 왜냐하면 모델의 컨텍스트에 들어가는 모든 것이 사실상 '입력'이기 때문이다.

먼저 믿을 수 있는 것을 정리하자.

시스템 프롬프트와 개발자 지시는 믿을 수 있다. 개발자가 직접 작성하고, 버전 관리되며, 배포 파이프라인을 통해 변경되는 영역이다. 물론 이것도 완벽하지 않다. 시스템 프롬프트가 유출되면(LLM08) 공격자의 재료가 되므로 보호 대상이지만, 출발점에서는 신뢰 영역으로 둔다.

애플리케이션 코드와 설정도 믿을 수 있다. 입력 검증 로직, 가드레일, 도구 호출 래퍼 같은 코드가 여기에 속한다. 다만 코드가 의존하는 외부 라이브러리는 공급망(LLM04) 관점에서 따로 검토한다.

다음은 믿을 수 없는 것들이다.

사용자 입력은 믿을 수 없다. 프롬프트 인젝션(LLM01)의 출발점이다. 사용자가 보낸 모든 텍스트는 악성일 수 있다고 가정한다.

외부 문서는 믿을 수 없다. RAG로 읽어오는 사내 문서, 웹 검색 결과, 업로드된 파일이 여기에 속한다. 문서 안에 숨겨진 지시문이 모델을 조종하는 간접 인젝션의 통로다.

도구 결과도 믿을 수 없다. 에이전트가 호출한 API나 검색 엔진이 돌려준 텍스트는 외부에서 온 데이터다. 신뢰 경계 밖에 있다. 도구 결과를 그대로 컨텍스트에 넣는 순간, 그 텍스트는 모델에게 '지시'처럼 보일 수 있다.

정리하면, LLM 앱의 신뢰 경계는 이렇게 그어진다. 경계 안: 시스템 프롬프트, 개발자 지시, 애플리케이션 코드. 경계 밖: 사용자 입력, 외부 문서, 도구 결과, 외부 API 응답. 경계를 넘는 데이터는 전부 검증과 정화의 대상이다.

## 공격 표면: 공격자가 건드릴 수 있는 지점

공격 표면은 10장에서 소개한 개념이다. 다시 정리하면, 공격자가 입력이나 조작을 시도할 수 있는 지점의 총합이다. 위협 모델링에서는 이 지점들을 빠짐없이 나열하는 것이 목표다.

일반적인 LLM 앱의 공격 표면 체크리스트는 다음과 같다.

1. 채팅 입력창과 API 엔드포인트. 직접 프롬프트 인젝션의 진입점이다.
2. 파일 업로드. 문서에 악성 지시를 숨기는 간접 인젝션의 진입점이다.
3. RAG 파이프라인. 임베딩 모델, 청킹 로직, 벡터 DB, 검색 쿼리가 모두 표면이다. 오염된 문서 주입(LLM05, LLM09)의 진입점이다.
4. 도구와 함수 호출. 에이전트가 쓸 수 있는 도구 목록 자체가 표면이다. 과도한 권한(LLM03)의 출발점이다.
5. 외부 연동. MCP 서버, 플러그인, 서드파티 API가 표면이다. 공급망(LLM04)의 진입점이다.
6. 출력 렌더링. 모델의 출력이 표시되는 웹 UI, 저장되는 DB, 전달되는 하류 시스템이 표면이다. 부적절한 출력 처리(LLM10)의 진입점이다.
7. 관리 인터페이스. 시스템 프롬프트를 바꾸는 관리자 페이지, 로그 뷰어, 비용 대시보드가 표면이다. 설정 변경과 정보 노출의 진입점이다.

이 목록을 자신의 앱에 대입해보자. 해당하지 않는 항목은 지우고, 빠진 항목은 추가한다. 예를 들어 음성 입력을 받는 앱이라면 음성 인식 파이프라인이 표면에 추가된다.

## 자산 식별: 지켜야 할 것

자산은 공격자가 노리는 가치 있는 것이다. LLM 앱의 자산은 생각보다 다양하다.

데이터 자산: 사용자 개인정보, 사내 문서, 학습 데이터, 벡터 DB의 원문, API 키와 비밀값. LLM02(민감 정보 노출)와 LLM08(히든 컨텍스트 노출)의 보호 대상이다.

행동 자산: 에이전트가 가진 도구 권한. 이메일 발송, 파일 삭제, 결제 승인, 코드 실행 같은 능력 자체가 자산이다. 공격자는 이 능력을 탈취하려 한다. LLM03(과도한 에이전시)의 핵심이다.

비용 자산: API 사용량과 추론 예산. LLM06(무제한 소비)의 표적이다.

신뢰 자산: 모델의 출력에 대한 사용자의 신뢰. LLM07(허위정보)이 훼손하는 자산이다.

자산을 식별할 때는 "이게 털리면 뭐가 일어나는가"를 함께 적는다. 그래야 방어의 우선순위가 정해진다. 예를 들어 결제 승인 도구가 있는 에이전트라면, 그 도구 권한이 최우선 보호 대상이 된다.

## 실습: 간단한 채팅봇 위협 모델링

이론은 여기까지다. 이제 간단한 사내 문서 Q&A 챗봇을 예제로 세 단계를 직접 해보자. 시스템 구성은 이렇다. 사용자가 질문을 입력하면, 챗봇이 사내 위키에서 관련 문서를 검색(RAG)해 답변한다. 관리자는 문서 업로드 페이지로 위키 문서를 추가할 수 있다.

1단계, 자산 목록을 작성한다.

- 사내 위키 문서 전체 (데이터 자산)
- 사용자 질문 로그 (데이터 자산, 개인정보 포함 가능)
- 문서 검색 도구와 답변 생성 파이프라인 (행동 자산)
- OpenAI 호환 API 키 (데이터 자산, 비용과 직결)
- 관리자 업로드 페이지 접근 권한 (행동 자산)

2단계, 신뢰 경계를 그린다.

- 경계 안: 시스템 프롬프트("사내 위키 내용으로만 답하라"), 검색·답변 파이프라인 코드, 관리자 인증 로직
- 경계 밖: 사용자 질문, 위키 문서(업로드된 파일), 검색 결과 스니펫

여기서 중요한 판단이 하나 있다. 위키 문서는 사내 문서지만 신뢰 경계 밖에 둔다. 관리자가 업로드하는 문서라도, 업로드 과정에서 오염될 수 있고(LLM05), 문서 안에 악성 지시가 숨어 있을 수 있기 때문이다(LLM01 간접 인젝션). "우리 문서니까 안전하다"는 가정이 가장 흔한 실수다.

3단계, 공격 표면을 나열한다.

- 질문 입력 API (직접 프롬프트 인젝션)
- 문서 업로드 페이지 (악성 문서 주입, 간접 인젝션)
- RAG 검색 결과 (검색된 문서 스니펫이 컨텍스트에 들어감)
- 답변 렌더링 UI (출력에 스크립트가 포함될 경우, LLM10)
- API 키 저장소 (유출 시 비용 폭증, LLM06과 연결)

여기까지 그리면 방어의 위치가 보인다. 입력 검증은 질문 API에, 문서 정화는 업로드 파이프라인에, 출력 검증은 렌더링 단계에 둔다. 도구 권한은 이 챗봇에 없으므로 LLM03의 우선순위는 낮다. 반면 문서 기반 간접 인젝션이 핵심 위협이므로 20장과 24장을 먼저 읽는 것이 효율적이다.

## NIST AI RMF와 연결하기

위협 모델링이 익숙하지 않다면 NIST의 AI RMF를 나침반으로 삼을 수 있다. NIST AI RMF 1.0(NIST AI 100-1)은 2023년 1월에 발행된 자발적 프레임워크로, Govern(거버넌스), Map(매핑), Measure(측정), Manage(관리)라는 4개 핵심 기능을 제시한다. 7가지 신뢰 특성을 함께 정의하고 있다. 참고로 2026년 9월 28일 기준으로 AI RMF 1.0의 개정 작업이 진행 중이며 v2.0은 아직 발행되지 않았다.

이 중 Map 단계는 위협 모델링과 직접 연결된다. Map은 AI 시스템의 인벤토리(무엇이 어디에 있는지 목록화)와 AI-BOM(AI Bill of Materials, 모델·데이터셋·라이브러리 등 구성 요소 명세)을 만들라고 요구한다. 이 장의 자산 목록과 공격 표면 나열이 바로 인벤토리의 출발점이다. 자신의 LLM 앱을 구성하는 모델, 임베딩 서비스, 벡터 DB, 도구, 외부 연동을 목록으로 적는 것부터 시작하면 된다.

Measure 단계는 레드팀 평가를 포함한다. 위협 모델링으로 그린 공격 표면을 실제로 공격해보는 단계다. 이 책의 Part 4(40장 레드티밍 방법론, 41장 보안 테스트 체크리스트)가 바로 Measure 단계의 실전 구현이다.

또한 NIST는 2024년 7월 26일에 AI 600-1(Generative AI Profile)을 최종 발행했다. 생성형 AI 고유의 위험 13개와 400개가 넘는 개발자 조치를 정리한 문서로, 2026년 10월 현재 후속 프로필은 나와 있지 않다. 위협 모델링을 마친 뒤 각 위험에 대한 구체적인 조치를 찾을 때 참고할 수 있다. 에이전트 보안에 특화된 흐름으로는 2026년 2월에 출범한 AI Agent Standards Initiative가 있으며, 에이전트의 보안과 아이덴티티를 중심으로 표준화 논의를 진행하고 있다.

위협 모델링은 한 번 그리고 끝나는 작업이 아니다. 앱에 도구가 하나 추가될 때마다, 외부 연동이 하나 늘어날 때마다 다시 그린다. 다음 장부터 시작되는 Part 2의 각 항목을 읽을 때마다, 이 장에서 그린 자신의 위협 모델에 방어선을 하나씩 추가해보자.

## 실습 결과물 예시: 방어 매핑표

위협 모델링의 결과물은 "그래서 뭘 할 것인가"로 이어져야 한다. 위 채팅봇 예제의 공격 표면에 Part 2와 Part 3의 장을 매핑하면 다음과 같은 표가 나온다.

| 공격 표면 | 주요 위협 | 대응 장 |
|---|---|---|
| 질문 입력 API | 직접 프롬프트 인젝션 (LLM01) | 20장, 30장 |
| 문서 업로드 페이지 | 악성 문서 주입, 간접 인젝션 (LLM01, LLM05) | 20장, 24장 |
| RAG 검색 결과 | 컨텍스트 오염, 히든 컨텍스트 노출 (LLM08) | 27장, 28장 |
| 답변 렌더링 UI | 스크립트 삽입 등 출력 처리 문제 (LLM10) | 29장, 30장 |
| API 키 저장소 | 키 유출, 비용 폭증 (LLM02, LLM06) | 21장, 25장 |

이 표가 위협 모델링의 최종 산출물이다. "어디가 뚫릴 수 있고, 그걸 막으려면 이 책의 어디를 읽어야 하는지"가 한 장에 정리된다. 팀에 공유할 때도 이 표 하나면 충분하다.

## AI-BOM 예시

NIST AI RMF의 Map 단계에서 요구하는 AI-BOM(AI Bill of Materials)은 "우리 AI 시스템이 무엇으로 구성됐는가"의 명세다. 위 채팅봇 예제의 AI-BOM을 JSON으로 적으면 다음과 같다.

```json
{
  "system": "사내 문서 Q&A 챗봇 v1.2",
  "model": {
    "name": "example-chat-model",
    "version": "2026-06",
    "provider": "외부 API",
    "api_key_ref": "vault://llm/api_key"
  },
  "embedding": {
    "name": "example-embedding-model",
    "version": "v3",
    "provider": "외부 API"
  },
  "vector_db": {
    "name": "example-vector-store",
    "version": "2.4.1",
    "deployment": "사내 서버"
  },
  "data_sources": [
    {"name": "사내 위키 스냅샷", "updated": "2026-10-01", "trust": "untrusted"},
    {"name": "관리자 업로드 문서", "updated": "수시", "trust": "untrusted"}
  ],
  "tools": [],
  "external_integrations": []
}
```

주목할 점은 data_sources의 trust 필드다. 사내 문서지만 untrusted로 표시했다. 12장 본문에서 말했듯이 "우리 문서니까 안전하다"는 가정을 버린 것이다. AI-BOM은 이렇게 각 구성 요소의 출처와 신뢰도를 명시하는 문서다. 도구가 추가되거나 모델 버전이 바뀌면 AI-BOM도 함께 업데이트한다.

## 흔한 실수 세 가지

위협 모델링을 처음 할 때 자주 나오는 실수를 정리한다.

첫째, "우리 문서는 안전하다"는 가정이다. 위 예제에서도 강조했지만, 내부 문서도 신뢰 경계 밖에 둔다. 문서 업로드 경로가 하나라도 열려 있으면 그 문서는 외부 입력과 다를 바 없다.

둘째, 도구를 과소평가하는 것이다. "검색 도구 하나쯤이야"라고 생각하기 쉽다. 하지만 도구는 모델의 손발이다. 검색 결과가 악성 지시를 포함하고 있으면, 그 도구는 공격자의 도구가 된다. 도구가 하나라도 있으면 LLM03(과도한 에이전시)의 관점에서 권한을 검토한다.

셋째, 출력 쪽을 빠뜨리는 것이다. 입력 보안만 신경 쓰고, 모델의 출력이 어디로 가는지는 안 그리는 경우가 많다. 출력이 웹 UI에 렌더링되는지, DB에 저장되는지, 다른 시스템의 입력이 되는지를 반드시 그린다. 출력이 다른 시스템의 입력이 되는 순간, 그 시스템도 공격 표면에 포함된다.

## 위협 모델링 체크리스트 스크립트

위협 모델링 결과를 간단한 스크립트로 점검할 수 있다. 아래는 공격 표면 항목마다 대응 장이 매핑됐는지 확인하는 예제다.

```python
# threat_model_check.py - 위협 모델링 결과 점검
attack_surface = {
    "질문 입력 API": ["20장", "30장"],
    "문서 업로드 페이지": ["20장", "24장"],
    "RAG 검색 결과": ["27장", "28장"],
    "답변 렌더링 UI": ["29장", "30장"],
    "API 키 저장소": ["21장", "25장"],
}

uncovered = [name for name, chapters in attack_surface.items() if not chapters]
if uncovered:
    print("대응 장이 없는 공격 표면:")
    for name in uncovered:
        print(" -", name)
else:
    print("모든 공격 표면에 대응 장이 매핑됐다.")
    print("총", len(attack_surface), "개 지점 점검 완료.")
```

실무에서는 이보다 복잡한 도구를 쓰겠지만, 핵심은 같다. 공격 표면을 빠짐없이 나열하고, 각 지점에 대응책을 매핑했는지 확인하는 것이다. 표면이 하나라도 비어 있으면 그곳이 다음 사고의 출발점이 된다.
