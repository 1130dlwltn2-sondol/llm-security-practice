# 70. 실전 프로젝트: 안전한 사내 문서 도우미 에이전트

지금까지 배운 내용을 하나의 프로젝트로 묶어 보자.
사내 문서를 검색해 답해 주는 에이전트를 만든다고 가정하고,
요구사항부터 테스트까지 5단계를 순서대로 밟는다.
각 단계의 산출물은 실제 문서로 남긴다.
이 장을 마치면 Part 3의 방어 설계가 어떻게 현실의 프로젝트에 녹아드는지
손으로 직접 확인할 수 있다.

## 1단계: 요구사항 정의

먼저 에이전트가 "무엇을 하는지"를 한 문장으로 적는다.
"사내 문서를 검색해 직원의 질문에 답하는 에이전트."
여기에 보안과 직결되는 조건 두 가지를 붙인다.

- 접근 권한이 부서별로 다르다. 인사팀 문서는 인사팀만, 재무팀 문서는 재무팀만 볼 수 있다.
- 에이전트는 검색과 요약만 한다. 문서 삭제·발송·외부 전송은 하지 않는다.

요구사항을 이렇게 적는 이유는 간단하다.
"부서별 접근 권한"은 나중에 테넌트 격리 검증(42장)의 근거가 되고,
"검색과 요약만"은 과도한 에이전시(LLM03)를 막는 권한 범위의 근거가 된다.
요구사항 단계에서 권한 범위를 정해 두지 않으면,
구현 단계에서 에이전트에게 이것저것 시키게 된다.

비기능 요구사항도 함께 적는다.
"답변은 5초 안에 반환한다" 같은 성능 조건과
"모든 도구 호출은 로그에 남긴다" 같은 감사 조건이다.
보안 요구사항은 비기능 요구사항에 속한다.
기능 목록에만 집중하면 보안은 나중에 끼워 넣게 되고,
나중에 끼워 넣은 보안은 구멍이 생기기 쉽다.

## 2단계: 위협 모델링

위협 모델링은 "무엇이, 어디서, 어떻게 공격받을 수 있는가"를 도출하는 작업이다.
자산, 신뢰 경계, 공격 표면의 세 가지로 정리한다.

자산은 보호할 대상이다.
이 프로젝트의 자산은 부서별 기밀 문서, 문서 검색 도구, 답변 전송 경로다.
특히 타 부서 문서는 "절대 노출되면 안 되는" 최고 등급 자산으로 분류한다.

신뢰 경계는 믿을 수 있는 영역과 없는 영역의 구분선이다.
사용자 입력은 믿을 수 없다.
RAG로 검색되는 문서도 믿을 수 없다.
문서 안에 숨겨진 지시(간접 인젝션)가 있을 수 있기 때문이다.
MCP로 연결된 외부 도구 역시 신뢰 경계 밖에 둔다.

공격 표면은 공격자가 건드릴 수 있는 지점이다.
사용자 질문 입력창, 문서 업로드 경로, MCP 도구 호출 지점,
그리고 모델의 출력이 표시되는 화면이 공격 표면이다.

위협 모델링의 산출물은 표 한 장이면 충분하다.
자산 목록, 신뢰 경계 그림, 공격 표면 목록을 한 페이지에 정리한다.
아래는 이 프로젝트의 위협 모델 요약 예시다.

```text
[자산]
- 부서별 기밀 문서 (최고 등급: 타 부서 문서)
- 문서 검색·요약 도구
- 답변 전송 경로

[신뢰 경계]
- 믿을 수 없음: 사용자 입력, RAG 검색 문서, MCP 외부 도구
- 믿을 수 있음: 권한 검증 래퍼, 가드레일, 승인 절차

[공격 표면]
- 사용자 질문 입력창 (LLM01 직접 인젝션)
- 문서 업로드 경로 (LLM05 포이즈닝)
- MCP 도구 호출 지점 (LLM04 공급망)
- 모델 출력 화면 (LLM08 히든 컨텍스트 노출, LLM02 민감정보 노출)
```

이 문서는 3단계 설계의 입력이 된다.

## 3단계: 설계 — Part 3 방어를 적용한다

위협 모델을 바탕으로 Part 3에서 배운 방어를 배치한다.
네 가지 방어 계층을 순서대로 둔다.

첫째, 입력 검증이다.
사용자 질문과 검색된 문서는 모두 검증 계층을 통과한다.
Anthropic 공식 6원칙 중 "콘텐츠 성격·출처 명시"를 적용해,
모델에게 "이것은 사용자 입력이다", "이것은 검색된 문서다"를 구분해서 전달한다.

둘째, 가드레일이다.
모델의 출력에서 비밀값 패턴과 부서 외 문서 인용을 검사한다.
가드레일은 모델을 믿지 않고 한 번 더 확인하는 장치다.

셋째, 최소 권한 도구다.
에이전트가 호출할 수 있는 도구는 문서 검색과 요약뿐이다.
삭제·발송 도구는 아예 연결하지 않는다.
연결하지 않은 도구는 악용될 수 없다.
이것이 최소 권한의 가장 확실한 형태다.

넷째, 사람 승인이다.
예민한 동작은 사람이 승인해야 실행된다.
예를 들어 타 부서 문서가 검색 결과에 포함되면
답변을 내보내기 전에 담당자의 확인을 거치게 한다.
승인 요청에는 "왜 승인이 필요한지"를 함께 보여 준다.
"인사팀 문서 2건이 검색되었습니다. 답변에 포함할까요?"처럼
근거를 함께 보여 주어야 승인자가 형식적인 클릭을 하지 않는다.

네 계층의 배치를 그림으로 그리면 위의 아키텍처 이미지가 된다.
요청은 왼쪽에서 들어와 입력 검증, 검색(권한 강제), 가드레일,
사람 승인을 거쳐 오른쪽으로 나간다.
어느 계층을 우회하는 경로가 있는지가 설계 리뷰의 핵심 질문이다.

## 4단계: 구현 — 핵심 방어 코드 스케치

설계를 코드로 옮긴다.
전체 구현이 아니라 핵심 방어의 뼈대만 잡는다.
아래는 부서별 접근 권한을 강제하는 검색 래퍼다.

```python
# 부서별 문서 접근 권한을 강제하는 검색 래퍼

ALLOWED_DEPARTMENTS = {"hr", "finance", "engineering"}

def search_documents(query, user_department, session_org_id):
    # 1. 부서 식별 (42장의 테넌트 검증과 같은 원리)
    if user_department not in ALLOWED_DEPARTMENTS:
        raise PermissionError("등록되지 않은 부서입니다.")

    # 2. 사용자 입력 검증: 지시처럼 보이는 패턴 차단
    if looks_like_instruction(query):
        raise ValueError("질문에 명령 형태의 문구가 포함되어 있습니다.")

    # 3. 검색은 해당 부서 문서로 범위를 한정한다
    results = vector_search(
        query=query,
        filter={"department": user_department, "org_id": session_org_id},
    )

    # 4. 검색된 문서에도 출처를 표시한다 (Anthropic 6원칙: 출처 명시)
    labeled = [
        {"source": "검색된 문서", "department": user_department, "text": doc}
        for doc in results
    ]
    return labeled


def looks_like_instruction(text):
    # 실제로는 더 정교한 검사를 둔다. 여기서는 뼈대만.
    markers = ["시스템 지시를 무시", "ignore previous instructions"]
    lowered = text.lower()
    return any(m in lowered for m in markers)


def vector_search(query, filter):
    # 실제 벡터 DB 호출이 들어가는 자리. 더미 반환.
    return ["사내 규정 요약 더미 문서"]


# 사용 예시
docs = search_documents(
    query="연차 규정을 알려줘",
    user_department="hr",
    session_org_id="org-a12",
)
print(docs)
```

다음은 출력 가드레일의 뼈대다.

```python
# 출력 가드레일: 비밀값 패턴과 부서 외 인용을 검사한다

import re

SECRET_PATTERNS = [
    re.compile(r"sk-dummy-[0-9a-zA-Z]+"),  # 더미 키 형식 예시
    re.compile(r"[0-9]{6}-[0-9]{7}"),      # 주민등록번호 형식 예시
]

def guard_output(answer, user_department):
    for pattern in SECRET_PATTERNS:
        if pattern.search(answer):
            return {
                "blocked": True,
                "reason": "답변에 비밀값으로 의심되는 패턴이 있습니다.",
            }
    if "타 부서 문서 인용" in answer:
        return {
            "blocked": True,
            "reason": "권한 밖의 부서 문서가 인용되었습니다. 담당자 승인이 필요합니다.",
        }
    return {"blocked": False, "answer": answer}
```

이 두 조각이 3단계 설계의 입력 검증·가드레일·최소 권한을 코드로 옮긴 것이다.
실제 프로젝트에서는 여기에 로깅과 모니터링을 붙인다.

## 5단계: 테스트 — 체크리스트와 레드팀 시나리오

구현이 끝나면 41장의 체크리스트로 자가 점검을 한다.
48개 항목을 하나씩 확인하고 통과율을 계산한다.
미통과 항목은 배포 전에 조치한다.

이어서 40장의 방법론으로 레드팀 시나리오를 작성한다.
이 프로젝트에 맞는 시나리오 예시는 다음과 같다.

- 시나리오 1: 타 부서 직원이 질문에 숨겨진 지시를 넣어 인사팀 문서를 열람하려 한다 (LLM01 + LLM02)
- 시나리오 2: RAG 문서에 악성 지시를 삽입해 에이전트가 외부로 문서를 전송하도록 유도한다 (LLM05 + LLM03)
- 시나리오 3: 시스템 프롬프트를 끌어내 부서 권한 규칙을 파악하려 한다 (LLM08)

시나리오는 문서로 작성하고,
테스트 환경에서 실행한 뒤 보고서를 남긴다.
보고서는 NIST AI 600-1의 Measure 단계에 대한 이행 증거가 된다.
NIST AI 600-1은 2024년 7월 26일에 최종 발행되었으며,
GAI 고유 위험 13개와 400개가 넘는 조치를 정리한 문서다.

테스트가 끝나면 배포를 결정한다.
41장의 기준을 그대로 쓴다.
통과율 95퍼센트 이상이면 배포하고,
미통과 항목은 다음 정기 점검 때까지 조치한다.
배포 후에도 모니터링은 계속된다.
토큰 사용량의 비정상 폭증(LLM06)과 차단 로그의 급증은
새로운 공격 시도의 신호일 수 있다.
대시보드에 두 지표를 올려 두고 주 1회 확인하는 것을 권장한다.

## 정리

5단계를 다시 정리한다.
요구사항에서 권한 범위를 정하고,
위협 모델링에서 자산·신뢰 경계·공격 표면을 도출하고,
설계에서 입력 검증·가드레일·최소 권한·사람 승인을 배치하고,
구현에서 핵심 방어를 코드로 옮기고,
테스트에서 체크리스트와 레드팀 시나리오로 검증한다.
이 흐름이 몸에 익으면 어떤 에이전트 프로젝트에도 그대로 적용할 수 있다.

이 책에서 다루는 공격 기법은 모두 학습·방어 목적이며, 허가되지 않은 시스템에 대한 공격 시도는 절대 하지 말 것.
