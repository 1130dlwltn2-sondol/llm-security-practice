# 28. LLM09 벡터·임베딩 취약점

RAG(검색 증강 생성) 시스템에서 모델의 답변 품질은 검색 품질에 달려 있다. 그런데 검색 결과를 오염시킬 수 있다면 어떻게 될까. LLM09 'Vector and Embedding Weaknesses(벡터·임베딩 취약점)'는 바로 이 지점을 다룬다. RAG나 유사도 검색에서 공격자가 모델이 '보는' 내용을 조종하는 위협이다.

OWASP LLM Top 10 2026년판에서 LLM09는 8위에서 9위로 한 계단 내려갔다. 순위는 소폭 하락했지만 여전히 Top 10에 들어 있는, RAG를 쓰는 조직이라면 피할 수 없는 주제다. 이 장에서는 임베딩 공간 조작의 원리를 직관적으로 이해하고, 권한 태그와 검색 필터링으로 방어하는 방법을 코드와 함께 다룬다. 특정 사고 사례는 다루지 않고 원리와 방어에 집중한다.

## 28.1 유사도 검색은 '의미상 가까움'에 의존한다

임베딩은 텍스트를 숫자들의 나열, 즉 벡터로 바꾸는 기술이다. 의미가 비슷한 문장은 벡터 공간에서도 가까운 위치에 놓인다. RAG의 검색 단계는 이 성질을 이용한다. 사용자 질문을 벡터로 바꾸고, 미리 벡터로 바꿔 둔 문서 조각(청크)들 중에서 '가장 가까운' 것들을 골라 모델에게 건네는 것이다.

여기서 핵심 한계를 짚어야 한다. 유사도 검색이 재는 것은 '의미상 가까움'이지, '사실 여부'나 '공개해도 되는 문서인지'가 아니다. 검색기는 질문과 비슷해 보이는 문서를 가져올 뿐, 그 문서가 믿을 만한지, 이 사용자가 봐도 되는 문서인지 판단하지 않는다. 이 판단의 공백이 공격 지점이다. 검색기를 '똑똑한 사서'로 착각하면 안 된다. 사서는 심부름꾼이지 심사관이 아니다.

초급자를 위한 비유를 들어보자. 도서관 사서가 "이 책 제목이 질문이랑 비슷하네요"라며 책을 가져다주는 것과 같다. 사서는 책의 내용이 사실인지, 대출 제한 도서인지 확인하지 않는다. 사서(검색기)의 역할은 '비슷한 것 찾기'에서 끝난다. 검증은 다른 장치가 해야 한다.

## 28.2 공격자가 '보는 내용'을 조종하는 방법

원리를 알면 공격의 그림이 보인다. 공격자가 문서 저장소에 악의적인 문서를 넣을 수 있다면, 검색 결과를 오염시킬 수 있다. 예를 들어 자주 묻는 질문과 의미상 가깝게 쓴 악성 문서를 심어 두면, 사용자가 그 주제를 물을 때마다 악성 문서가 검색 상위에 뜬다. 모델은 검색된 문서를 근거로 답하므로, 오염된 문서가 곧 오염된 답변이 된다.

또 다른 문제는 권한이 섞이는 것이다. 임원용 문서와 일반 직원용 문서가 같은 인덱스에 태그 없이 들어 있으면, 일반 직원의 질문에 임원용 문서가 검색될 수 있다. 공격자가 의도적으로 권한 경계를 넘나드는 질문을 던지면, 모델이 "검색된 근거"라는 명분으로 기밀 내용을 뱉어낼 수 있다. 검색기는 권한을 모르고, 모델은 검색된 것을 의심하지 않는다.

정리하면 공격의 구조는 이렇다. 첫째, 공격자가 문서 저장소에 영향을 준다(악성 문서 등록, 권한 태그 조작). 둘째, 오염된 문서가 정상 사용자의 질문에 검색된다. 셋째, 모델이 그 문서를 근거로 답을 만든다. 방어는 첫째 단계(등록 시 검사, 28.6절)와 둘째 단계(권한 필터, 28.4절)에 둔다. 셋째 단계, 즉 모델이 본 뒤에는 이미 늦다.

두 경우 모두 구조는 같다. '무엇을 보여줄지'를 정하는 검색 단계가 공격자의 영향권에 들어가고, 모델은 주어진 것을 그대로 믿는다. 그래서 방어는 검색 단계, 즉 모델이 보기 전에 개입해야 한다.

여기서 한 가지 더 짚자. 임베딩 모델 자체를 공격자가 고를 수 있는 경우는 드물지만, 임베딩 모델이 바뀌면 유사도 분포가 달라진다. 모델을 교체할 때는 28.5절의 임계값을 처음부터 다시 튜닝해야 한다. 이전 모델에서 잘 동작하던 숫자를 그대로 가져오면 필터가 헐거워지거나 답변이 빈약해진다.

## 28.3 방어 1: 청크에 권한 태그를 붙여라

첫 번째 방어는 문서를 인덱스에 넣는 시점에 권한 정보를 함께 기록하는 것이다. 청크마다 "누가 볼 수 있는 문서인지"를 메타데이터로 태깅한다.

```python
chunk = {
    "text": "2026년 하반기 임원 성과급 지급 기준은...",
    "metadata": {
        "doc_id": "hr-2026-h2",
        "department": "hr",
        "clearance": "executive",   # 공개 범위: public, internal, executive 등
        "owner": "hr-team",
    },
    "embedding": [0.12, -0.34, 0.56],  # 실제 임베딩 벡터
}
```

권한 태그의 설계 원칙은 단순해야 한다. 태그 종류가 너무 많아지면 관리가 안 되고, 결국 필터에 구멍이 생긴다. 보통은 3~4단계의 공개 범위(public, internal, confidential, executive)와 부서 태그 정도면 충분하다. 태그는 문서 등록 파이프라인에서 자동으로 부여되게 하고, 사람이 일일이 지정하게 두지 않는 것이 좋다. 사람이 지정하면 빠뜨리는 경우가 생기기 때문이다.

중요한 점 하나. 태그는 검색기가 이해하는 언어로 적어야 한다. 자연어로 "이 문서는 임원만 보세요"라고 본문에 쓰는 것은 태그가 아니다. 검색기는 본문의 주의 문구를 권한으로 해석하지 않는다. 구조화된 메타데이터 필드로 넣어야 필터링에 쓸 수 있다.

태그 부여는 자동화하는 것이 좋다. 문서 등록 파이프라인에서 저장 경로(예: /hr/executive/)나 문서 관리 시스템의 분류 필드에서 권한을 추론해 자동으로 붙이는 방식이다. 사람이 일일이 지정하게 두면 빠뜨리는 경우가 생기고, 태그가 빠진 문서는 28.8절 실습의 정책대로 차단되므로 업무에 지장이 생긴다. 자동 부여와 등록 시 검사를 함께 쓰는 것이 정석이다.

## 28.4 방어 2: 검색 후 필터링하라

태그를 붙였다면, 검색 결과를 모델에게 건네기 전에 사용자의 권한과 대조해 걸러낸다. 순서는 '검색 후 필터링'이 표준이다. 벡터 검색 자체는 전체 인덱스에서 수행하고, 결과 중에서 권한에 맞는 것만 남기는 방식이다.

```python
CLEARANCE_ORDER = {"public": 0, "internal": 1, "confidential": 2, "executive": 3}

def filter_by_clearance(results: list, user_clearance: str) -> list:
    user_level = CLEARANCE_ORDER[user_clearance]
    allowed = []
    for r in results:
        doc_level = CLEARANCE_ORDER[r["metadata"]["clearance"]]
        if doc_level <= user_level:
            allowed.append(r)
    return allowed

def filter_by_department(results: list, user_dept: str) -> list:
    allowed = []
    for r in results:
        meta = r["metadata"]
        # 부서 제한이 없는 문서는 통과, 제한이 있으면 소속 부서만 통과
        if meta.get("department") in (None, user_dept):
            allowed.append(r)
    return allowed

# 사용 예: 검색 결과 10건 중 권한에 맞는 것만 남긴 뒤 상위 3건을 모델에 전달
# filtered = filter_by_department(filter_by_clearance(raw_results, "internal"), "sales")
# context = filtered[:3]
```

이 필터는 모델이 아니라 코드로 동작해야 한다. 모델에게 "권한 없는 문서는 인용하지 마"라고 지시하는 것은 프롬프트에 의존하는 방어라서 우회될 수 있다. 검색 결과를 코드가 먼저 잘라내고, 잘린 뒤의 것만 모델에게 보여주는 구조가 안전하다.

필터링 전후의 건수는 로그에 남긴다. "검색 10건 중 권한 필터로 4건 제외" 같은 기록이 쌓이면, 특정 주제에서 권한 밖 문서가 자주 검색되는 패턴을 발견할 수 있다. 28.6절의 오염 탐지와 연결되는 지점이다.

또 하나 실무 팁. 필터링으로 걸러진 문서가 있었다는 사실 자체를 로그에 남긴다. "권한 밖 문서 N건이 검색됐으나 제외됨" 같은 기록은, 누군가 권한 경계를 두드리고 있다는 신호가 될 수 있다.

## 28.5 방어 3: 임계값을 설정하라

유사도 점수에는 임계값(threshold)을 둔다. 점수가 일정 수준을 넘지 못하는 문서는 관련성이 낮다고 보고 버린다. 임계값 없이 상위 N건을 무조건 가져가면, 관련 없는 문서까지 컨텍스트에 들어가 모델을 헷갈리게 하거나 공격자의 여지를 준다.

```python
def apply_threshold(results: list, min_score: float = 0.75) -> list:
    return [r for r in results if r.get("score", 0.0) >= min_score]

# 파이프라인 순서: 검색 -> 임계값 -> 권한 필터 -> 상위 K건
def build_context(raw_results: list, user: dict, top_k: int = 3) -> list:
    scored = apply_threshold(raw_results, min_score=0.75)
    cleared = filter_by_clearance(scored, user["clearance"])
    scoped = filter_by_department(cleared, user["department"])
    return scoped[:top_k]
```

임계값은 데이터셋마다 다르게 잡아야 한다. 너무 높으면 답변이 빈약해지고, 너무 낮으면 잡음이 들어간다. 운영 초기에는 로그를 보며 조정하고, 기준을 정한 뒤에는 함부로 낮추지 않는다. 임계값을 낮추는 것은 곧 공격자가 검색 결과에 끼어들 여지를 넓히는 일이다.

임계값과 top-k(가져올 문서 수)는 함께 조정해야 한다. top-k를 크게 잡으면 관련 없는 문서가 섞일 확률이 올라가므로 임계값을 높여 잡음으로 걸러내고, top-k를 작게 잡으면 임계값을 조금 낮춰도 된다. 두 값은 따로 노는 숫자가 아니라 하나의 세트로 관리한다. 변경할 때는 30.5절의 검증 규칙 버전 관리처럼 기록을 남긴다.

## 28.6 검색 결과 오염을 탐지하라

방어 1~3이 '들어오는 것을 걸러내는' 방어라면, 오염 탐지는 '이미 들어와 있는 것을 찾아내는' 방어다. 문서 저장소에 악성 문서가 심어졌을 때 알아차리는 장치다.

실무 방법은 세 가지다.

첫째, 문서 등록 파이프라인을 검사한다. 새 문서가 등록될 때 권한 태그가 있는지, 태그가 비어 있지는 않은지 확인한다. 태그 없는 문서는 28.8절 실습의 권장 정책처럼 기본적으로 차단하거나 최고 권한으로 취급한다. 등록 단계에서 걸러내면 인덱스가 오염될 일이 줄어든다.

둘째, 이상 징후를 모니터링한다. 특정 문서가 평소보다 훨씬 자주 검색 상위에 오르거나, 특정 주제의 검색 결과 구성이 갑자기 바뀌면 조사한다. 검색 로그는 가드레일의 탐지 재료가 된다. 31장의 휴리스틱 탐지와 같은 발상이다.

셋째, 문서 출처를 다양화한다. 하나의 출처에서 온 문서만으로 답을 만들지 않고, 여러 출처의 문서를 교차 확인하게 한다. 26장의 검증 계층과 같은 발상이다. 단일 문서에 의존하는 답변 구조는 그 문서 하나가 오염되면 그대로 무너진다.

```python
def validate_on_ingest(chunk: dict) -> dict:
    meta = chunk.get("metadata", {})
    if "clearance" not in meta:
        return {"ok": False, "reason": "권한 태그 누락. 등록 거부."}
    if meta["clearance"] not in CLEARANCE_ORDER:
        return {"ok": False, "reason": "알 수 없는 권한 등급."}
    return {"ok": True, "reason": ""}

# 등록 파이프라인에 붙이는 예시
def ingest(chunks: list) -> dict:
    accepted, rejected = [], []
    for c in chunks:
        r = validate_on_ingest(c)
        (accepted if r["ok"] else rejected).append(c)
    return {"accepted": len(accepted), "rejected": len(rejected)}
```

오염 탐지의 로그는 31장의 가드레일 감사 로그와 같은 저장소에 쌓아, 공격 패턴 분석에 함께 쓴다. 등록 단계의 검사와 검색 단계의 모니터링이 같은 그림을 그리게 만드는 것이 목적이다.

## 28.7 청크를 나눌 때 권한 경계를 지키라

문서를 청크로 나누는 과정에서도 보안 이슈가 생긴다. 하나의 문서 안에 공개 범위가 다른 섹션이 섞여 있을 때다. 예를 들어 앞부분은 전사 공개, 뒷부분은 임원 전용인 문서가 있다고 하자. 이를 기계적으로 500자씩 자르면, 임원 전용 내용이 전사 공개 청크에 딸려 들어갈 수 있다.

대책은 두 가지다. 첫째, 문서를 나눌 때 권한 경계를 기준으로 먼저 자른다. 섹션별로 권한이 다르면 섹션 단위로 청크를 만든다. 둘째, 그게 어려우면 문서 전체를 가장 높은 권한 등급으로 태깅한다. 일부가 과도하게 보호되는 셈이지만, 유출보다는 낫다.

```python
def tag_sections(sections: list) -> list:
    # 섹션: {"text": ..., "clearance": ...}
    chunks = []
    for sec in sections:
        chunks.append({
            "text": sec["text"],
            "metadata": {"clearance": sec["clearance"]},
        })
    return chunks

def tag_whole_document(text: str, clearances: list) -> dict:
    # 섹션 분리가 어려우면 문서 전체를 최고 등급으로
    order = {"public": 0, "internal": 1, "confidential": 2, "executive": 3}
    top = max(clearances, key=lambda c: order[c])
    return {"text": text, "metadata": {"clearance": top}}
```

청크 분할은 흔히 성능 관점에서만 다루지만, 보안 관점에서도 설계 대상이다. RAG 파이프라인을 만들 때 "이 문서를 어떻게 자를 것인가"는 "이 문서를 누구에게 보여줄 것인가"와 함께 결정해야 한다.

## 28.8 실습: 메타데이터 권한 태그 기반 검색 필터 구현

이번 장의 실습은 28.3절과 28.4절의 코드를 합쳐 작은 RAG 방어 파이프라인을 만드는 것이다. 실제 벡터 DB 없이도 로컬에서 안전하게 따라 할 수 있다.

목표: 권한 태그가 붙은 청크 목록에서, 사용자 권한에 맞는 것만 골라 모델에 전달할 컨텍스트를 만드는 함수를 완성한다.

1. 새 파이썬 파일을 만들고, 아래 샘플 데이터를 복사한다.

```python
CHUNKS = [
    {"text": "점심 메뉴 안내", "metadata": {"clearance": "public", "department": None}, "score": 0.91},
    {"text": "영업팀 실적 집계 방식", "metadata": {"clearance": "internal", "department": "sales"}, "score": 0.88},
    {"text": "임원 성과급 지급 기준", "metadata": {"clearance": "executive", "department": "hr"}, "score": 0.86},
    {"text": "전사 공지: 보안 교육 일정", "metadata": {"clearance": "internal", "department": None}, "score": 0.70},
]
```

2. 28.4절의 filter_by_clearance, filter_by_department와 28.5절의 apply_threshold, build_context를 구현한다.
3. 다음 사용자로 테스트하고 결과를 확인한다.
   - 일반 직원: clearance "internal", department "sales"
   - 임원: clearance "executive", department "hr"
4. 확인할 것: 일반 직원의 컨텍스트에 "임원 성과급 지급 기준"이 들어가지 않는지, 점수 0.70인 공지가 임계값 0.75에서 제외되는지. 영업팀 문서가 임원 사용자에게는 제외되는지도 확인한다. 권한 필터는 양방향으로 동작해야 한다.
5. 보너스 과제: 태그가 없는 청크(메타데이터 누락)가 들어오면 어떻게 처리할지 정책을 정하고 코드에 반영한다. 권장 정책은 '태그 없으면 가장 높은 권한으로 간주하고 차단'이다. 허용이 기본값이면 태그 누락이 곧 유출 경로가 되기 때문이다.
6. 추가 과제: 임계값을 0.75에서 0.9로 올리고, 다시 0.5로 낮춰 보며 각 사용자의 컨텍스트가 어떻게 바뀌는지 관찰한다. 임계값 변경이 검색 결과에 미치는 영향을 체감하는 것이 과제다. 28.5절에서 말한 "임계값을 낮추는 것은 공격자의 여지를 넓히는 일"을 숫자로 확인해 본다.
7. 완성된 build_context를 간단한 질의응답 흐름에 붙여 본다. 사용자 권한을 바꿔 가며 같은 질문을 던지고, 권한 없는 문서가 모델에 전달되는 컨텍스트에 들어가지 않는 것을 확인한다.

## 28.9 정리

- LLM09 벡터·임베딩 취약점은 OWASP LLM Top 10 2026년판에서 8위에서 9위로 이동한 위협이다. RAG를 쓰는 조직이라면 피할 수 없는 주제다.
- 유사도 검색은 '의미상 가까움'만 잰다. 사실 여부와 공개 가능 여부는 판단하지 않는다. 이 공백이 공격 지점이다.
- 방어는 모델이 보기 전에 개입한다. 청크 권한 태깅, 검색 후 권한 필터링, 유사도 임계값의 세 겹이다.
- 필터는 모델의 판단이 아니라 코드로 동작해야 한다. 태그가 없는 문서는 기본적으로 차단하는 쪽으로 정책을 잡는다.
- 청크 분할은 성능 문제가 아니라 보안 설계 대상이다. 권한 경계를 기준으로 자른다.
- 임계값과 top-k는 세트로 관리하고, 임베딩 모델 교체 시 처음부터 다시 튜닝한다.
- 검색 로그를 모니터링해 오염 징후를 조기에 발견한다. 등록 파이프라인의 검사와 함께 쓴다.

이 책에서 다루는 공격 기법은 모두 학습·방어 목적이며, 허가되지 않은 시스템에 대한 공격 시도는 절대 하지 말 것.
