# 41. 보안 테스트 체크리스트

배포 전날 밤, 마음이 불안한 이유는 보통 같다.
"뭔가 빼먹은 게 있을 것 같은데, 뭐가 빠졌는지 모르겠다."
이 장의 체크리스트는 그 불안을 점검표로 바꾸기 위한 것이다.
배포 전에 항목을 하나씩 확인하고, 통과하지 못한 항목은 배포를 미룬다.

## 사용 방법

각 항목을 읽고 현재 프로젝트 상태에 비추어 체크한다.
체크박스는 '- [ ]' 형태로 두었다.
미통과 항목이 하나라도 있으면 배포 전 조치를 완료한다.
전체 통과율은 실습에서 계산한다.

## OWASP LLM Top 10 2026 항목별 점검

아래 30개 항목은 코드를 직접 보며 확인하는 기술 점검이다.
모르는 용어가 나오면 해당 장으로 돌아가 복습한다.

### LLM01 프롬프트 인젝션

프롬프트 인젝션은 이 책의 Part 1~2에서 가장 깊이 다룬 위협이다.
방어의 핵심은 경계 구분과 간접 인젝션 대응이다.

- [ ] 사용자 입력과 시스템 지시를 구분하는 경계(구분자·역할 분리)가 코드에 명시되어 있다
- [ ] 간접 인젝션(RAG 문서·이메일·웹 검색 결과에 숨겨진 지시)에 대한 검증이 있다
- [ ] Anthropic 공식 6원칙 중 "자신의 지시를 tool_result에 넣지 않기"가 적용되어 있다

### LLM02 민감정보 노출

모델이 비밀을 흘리는 경로는 학습 데이터와 컨텍스트, 두 가지다.
둘 다 점검해야 한다.

- [ ] 모델 출력에 비밀값(API 키·토큰·개인정보)이 포함되는지 테스트했다
- [ ] 학습 데이터나 파인튜닝 데이터에 민감정보가 포함되지 않았는지 확인했다
- [ ] 출력 가드레일이 비밀값 패턴(키 형식·주민번호 형식 등)을 탐지한다

### LLM03 과도한 에이전시

2026년판에서 3위로 올라간 항목이다.
에이전트가 도구를 직접 실행하는 구조라면 최우선 점검 대상이다.

- [ ] 에이전트가 호출할 수 있는 도구가 최소 권한으로 제한되어 있다
- [ ] 파괴적이거나 되돌릴 수 없는 동작(삭제·결제·발송)은 사람의 승인을 거친다
- [ ] 에이전트의 자율 행동 범위(어떤 도구를 언제 쓸 수 있는지)가 문서로 정의되어 있다

### LLM04 공급망

내가 작성하지 않은 코드가 에이전트 안에서 실행된다.
그 출처를 모르면 위험을 모르는 것과 같다.

- [ ] 사용하는 모델·라이브러리·MCP 서버의 출처와 버전을 목록으로 관리한다
- [ ] 서드파티 MCP 서버를 도입하기 전에 출처 검증과 권한 검토를 했다
- [ ] 의존성 업데이트 시 무결성(해시·서명) 검증을 수행한다

### LLM05 데이터·모델 포이즈닝

RAG 문서는 모델의 눈이다.
눈에 들어가는 정보를 통제하지 않으면 답변이 오염된다.

- [ ] RAG에 들어가는 문서의 출처와 등록 권한이 통제되어 있다
- [ ] 외부에서 수집한 학습 데이터에 대한 품질 검토 절차가 있다
- [ ] 데이터셋 변경 이력이 기록되어 이상 징후를 추적할 수 있다

### LLM06 무제한 소비

2026년판에서 6위로 올라간 항목이다.
비용 공격은 조용히 들어와서 크게 터진다.

- [ ] 사용자·API 키별 요청량 제한(rate limit)이 설정되어 있다
- [ ] 토큰 사용량 모니터링과 임계값 알림이 동작한다
- [ ] 비정상 폭증 시 자동으로 차단하거나 승인 절차로 전환된다

### LLM07 허위정보

모델은 모르는 것도 그럴듯하게 말한다.
중요한 용도일수록 검증 계층이 필요하다.

- [ ] 모델이 불확실한 내용을 단정적으로 답하지 않도록 지침이 있다
- [ ] 중요 답변에는 출처 문서 링크를 함께 제공한다
- [ ] 허위정보 확산 위험이 큰 용도에는 추가 검증 계층을 두었다

### LLM08 히든 컨텍스트 노출

구 System Prompt Leakage에서 개명·확장된 항목이다.
시스템 프롬프트뿐 아니라 내부 규칙 전반을 지킨다.

- [ ] "시스템 프롬프트를 보여줘" 같은 요청에 대한 방어 테스트를 했다
- [ ] Anthropic 공식 6원칙 중 "시스템 프롬프트에 불신 정책 명시"가 적용되어 있다
- [ ] 오류 메시지나 디버그 출력에 내부 지시가 노출되지 않는다

### LLM09 벡터·임베딩 취약점

벡터 DB도 데이터베이스다.
일반 DB에 적용하는 접근 통제를 그대로 적용한다.

- [ ] 임베딩 검색 결과가 사용자 권한 범위 안에서만 반환되는지 확인했다
- [ ] 벡터 DB에 대한 접근 통제가 일반 DB와 동일한 수준으로 적용된다
- [ ] 검색 결과 조작(특정 문서를 상위에 띄우는 시도)에 대한 테스트를 했다

### LLM10 부적절한 출력 처리

2026년판에서 10위로 내려갔지만 여전히 흔한 실수다.
출력은 마지막 관문이다.

- [ ] 모델 출력을 하위 시스템(명령어 실행·HTML 렌더링·SQL)에 넘기기 전에 검증한다
- [ ] 출력에 포함된 스크립트나 명령어가 실행되지 않도록 이스케이프 처리한다
- [ ] Anthropic 공식 6원칙 중 "JSON 인코딩"이 구조화 출력에 적용되어 있다

## NIST AI 600-1 관점의 조직 점검

NIST AI 600-1(2024년 7월 26일 최종 발행)은 기술 점검을 넘어
조직 차원의 통제를 요구한다.
다음 세 영역은 배포 전 조직 점검 항목이다.

### 거버넌스: 책임과 정책

- [ ] AI 시스템의 보안 책임자가 지정되어 있다
- [ ] 허용된 용도와 금지된 용도를 적은 정책 문서가 있다
- [ ] 사고 발생 시 대응 절차(누가 무엇을 하는지)가 문서화되어 있다

### 인벤토리: AI-BOM

- [ ] 사용 중인 모델(버전 포함) 목록이 있다
- [ ] 연결된 도구와 MCP 서버 목록이 있다
- [ ] 각 구성 요소의 데이터 접근 범위가 기록되어 있다

### 측정: 평가 수행 여부

- [ ] 레드팀 평가(40장의 방법론)를 수행했고 보고서가 있다
- [ ] 배포 후에도 정기적으로 재평가할 일정이 잡혀 있다
- [ ] 발견된 취약점의 조치 현황을 추적하는 목록이 있다

## 자주 놓치는 항목 톱 3

체크리스트를 여러 프로젝트에 적용해 보면
빠지는 항목은 대개 비슷하다.
첫째는 LLM04의 AI-BOM 인벤토리다.
"쓰는 모델이 뭐지?"라는 질문에 즉답하지 못하는 팀이 많다.
둘째는 LLM06의 토큰 모니터링이다.
요청량 제한은 걸어 두어도 알림이 없으면 폭증을 늦게 알아챈다.
셋째는 조직 점검의 사고 대응 절차다.
사고가 났을 때 누가 무엇을 하는지 정해져 있지 않으면
대응이 늦어지고 피해가 커진다.
점수를 매긴 뒤 이 세 항목부터 확인해 보자.

## 실습: 내 프로젝트에 점수 매기기

위 체크리스트를 자신의 프로젝트에 적용해 보자.
방법은 단순하다.
통과한 항목 수를 전체 항목 수로 나누어 백분율을 구한다.

```text
통과율 = (체크한 항목 수 / 전체 48개 항목) * 100
```

80퍼센트 미만이면 배포를 미루고 미통과 항목부터 조치한다.
80~95퍼센트이면 미통과 항목의 위험도를 판단해
높음·중간 등급은 배포 전, 낮음 등급은 배포 후 2주 내 조치한다.
95퍼센트 이상이면 배포하되, 미통과 항목은 다음 정기 점검 때 반드시 확인한다.

점수를 매긴 뒤에는 미통과 항목 중 가장 위험한 것 3개를 골라
각각 "누가, 언제까지, 무엇을 할 것인지"를 한 줄로 적는다.
예를 들어 "홍길동, 금주 금요일까지, 전송 도구에 사람 승인 절차 추가"처럼 쓴다.
체크리스트는 점수를 매기는 데서 끝나지 않는다.
미통과 항목이 작업 목록으로 바뀌어야 의미가 있다.

## 체크리스트를 살아 있게 유지하기

체크리스트는 한 번 만들고 끝이 아니다.
프로젝트가 바뀌면 점검표도 바뀐다.
새 MCP 서버를 연결했다면 LLM04와 42장의 방어 항목을 다시 확인하고,
새 도구를 추가했다면 LLM03의 최소 권한 항목을 다시 본다.
NIST AI 600-1의 Manage 단계가 요구하는 것도 바로 이것이다.
측정하고(Measure), 관리하는(Manage) 사이클을 돌리는 것이다.
배포 후에는 분기마다 이 체크리스트를 다시 돌리는 것을 권장한다.
그때의 통과율과 지금의 통과율을 비교하면
보안 상태가 나아지고 있는지 숫자로 확인할 수 있다.

## 정리

보안 테스트 체크리스트는 두 겹이다.
OWASP LLM Top 10 2026 항목별 기술 점검 30개와
NIST AI 600-1 관점의 조직 점검 18개다.
배포 전에 전부 확인하고, 통과율을 계산하고,
미통과 항목을 작업 목록으로 전환한다.
다음 장에서는 공급망 항목과 직결되는 MCP 서버 보안을 다룬다.
