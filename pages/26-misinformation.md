# 26. LLM07 허위정보

잘못된 답을 내놓는 모델보다 무서운 것은, 틀린 답을 확신에 차서 내놓는 모델이다. LLM07 'Misinformation(허위정보)'은 바로 이 문제를 다룬다. 그럴듯하지만 사실이 아닌 모델 출력이 잘못된 인간의 결정, 혹은 잘못된 자동 결정을 유발하는 위험이다.

OWASP가 발간하는 LLM Top 10의 2026년판에서 LLM07은 9위에서 7위로 두 계단 상승했다. 순위가 올랐다는 것은 이 위협이 현실에서 더 자주, 더 심각하게 관찰되고 있다는 뜻이다. 모델이 똑똑해질수록 출력은 더 그럴듯해지고, 사람은 그럴듯함을 정확함으로 착각하기 쉬워진다. 이 장에서는 허위정보가 왜 생기는지, 어디에서 가장 위험한지, 그리고 실무에서 바로 쓸 수 있는 방어 방법을 코드와 함께 다룬다.

이 장에서는 특정 사고 사례를 다루지 않는다. 허위정보 사고는 대개 "모델이 틀렸다"는 한 줄로 요약되지만, 방어 설계에서 실제로 중요한 것은 틀린 출력이 어떤 경로로 의사결정에 들어갔는가이다. 이 장은 그 경로와 차단 방법에 집중한다.

## 26.1 왜 모델은 그럴듯하게 틀리는가

언어 모델은 사실을 '알고' 말하는 것이 아니라, 다음에 올 법한 토큰을 예측해서 말하는 존재다. 학습 데이터에 없는 내용, 모호한 질문, 애매한 맥락이 주어지면 모델은 빈틈을 그럴듯한 문장으로 메운다. 이를 보통 할루시네이션(hallucination)이라고 부른다.

할루시네이션 자체는 모델의 동작 방식에서 비롯된 현상이다. 이것이 보안 문제, 즉 'Misinformation'이 되는 것은 출력이 의사결정에 쓰일 때다. 참고용으로 읽고 버려지는 답과, 그대로 고객에게 전달되거나 다음 자동화 단계의 입력이 되는 답은 위험도가 완전히 다르다.

초급자를 위해 핵심을 한 줄로 정리하면 이렇다. 모델의 출력은 '정확한 문장'이 아니라 '정확해 보이는 문장'이다. 이 차이를 시스템 설계에 반영하는 것이 이 장의 목표다.

모델이 "모른다"고 말하지 못하는 것도 한 원인이다. 학습 과정에서 "모른다"는 답은 거의 보상을 받지 못한다. 아는 척하는 답이 더 높은 평가를 받는 구조에서 자란 모델에게, 정직한 불확실성은 기본값이 아니다. 그래서 26.5절의 불확실성 전달은 프롬프트와 출력 형식으로 '뒤늦게 가르쳐야 하는' 것이다.

자주 오해하는 지점이 하나 있다. "최신 모델은 할루시네이션이 줄었으니 괜찮지 않나?"라는 생각이다. 틀린 답의 비율은 줄었을지 몰라도, 남은 틀린 답은 이전보다 훨씬 그럴듯해졌다. 틀린 비율이 낮아지면 사람은 검증을 더 소홀히 하게 된다. 결과적으로 사고 한 건의 파급력은 오히려 커질 수 있다.

## 26.2 두 개의 피해 경로: 사람과 자동화

허위정보가 피해를 만드는 경로는 크게 두 가지다.

첫째, 사람이 그대로 믿는 경우다. 모델의 문체는 자신감 넘치고 논리적이라, 독자는 사실 확인을 건너뛰기 쉽다. 고객 상담 챗봇이 존재하지 않는 환불 정책을 안내하거나, 사내 도우미가 틀린 보안 가이드를 전파하는 식이다. 사람은 모델의 '태도'를 보고 신뢰도를 판단하는 경향이 있는데, 모델의 태도와 정확도는 아무 상관이 없다. 정중하고 단호한 문체로 틀린 말을 하는 모델이 가장 위험하다.

둘째, 자동화 파이프라인에 그대로 들어가는 경우다. 모델 출력을 검증 없이 다음 단계의 입력으로 쓰는 구조다. 예를 들어 모델이 생성한 요약을 임원이 그대로 결재 자료로 쓰거나, 모델이 내놓은 '문제없음' 판정을 배포 파이프라인이 승인 신호로 받아들이는 경우다. 사람이 중간에 없으니 틀린 출력이 걸러질 기회 자체가 없다. 자동화될수록 허위정보의 영향 범위는 커진다.

두 경로 모두 공통점이 있다. 출력이 '검증되지 않은 채로' 의사결정 단계에 들어간다는 점이다. 따라서 방어는 한 가지 원칙으로 수렴한다. 모델의 출력을 최종 결정으로 취급하지 말고, 검증 가능한 형태로 만들어라.

## 26.3 방어 1: 출처 표기를 강제하라

가장 기본적인 방어는 답과 근거를 분리하는 것이다. 모델에게 "답만 내지 말고, 어떤 근거에서 답했는지 함께 표시하라"고 요구한다. 출처가 없는 답은 일단 의심하고, 출처가 있는 답은 출처를 열어 확인한다.

시스템 프롬프트에 출처 표기를 강제하는 예는 다음과 같다.

```text
당신은 사내 지식베이스를 기반으로 답변하는 어시스턴트입니다.
규칙:
1. 답변의 모든 핵심 주장에는 근거 문서의 번호를 [출처: 문서번호] 형태로 표시합니다.
2. 근거 문서에서 확인할 수 없는 내용은 "확인할 수 없습니다"라고 답합니다.
3. 근거 없이 알고 있는 내용으로 추측해서 답하지 않습니다.
```

프롬프트만으로는 부족하다. 모델이 규칙을 어기고 출처 없이 답할 때가 있기 때문이다. 그래서 후처리 단계에서 출처 표기 유무를 검사하는 함수를 둔다.

```python
import re

CITATION_PATTERN = re.compile(r"\[출처:\s*[^\]]+\]")

def require_citation(answer: str) -> str:
    if CITATION_PATTERN.search(answer):
        return answer
    return (
        "이 답변에는 출처 표기가 없어 자동으로 차단되었습니다. "
        "근거 문서를 확인한 뒤 다시 질문해 주세요. [출처: 시스템 가드레일]"
    )

# 사용 예
raw = "환불은 30일 이내에 가능합니다."
print(require_citation(raw))
```

이 함수는 단순하지만 중요한 역할을 한다. '출처 없는 답은 사용자에게 전달하지 않는다'는 정책을 코드로 강제하는 것이다. 실제 운영에서는 차단 대신 "출처 확인 중"이라는 폴백 응답을 내보내거나, 근거 문서를 첨부해 재질문을 유도하는 방식으로 다듬으면 된다.

## 26.4 방어 2: 검증 계층을 두어라

출처 표기는 어디까지나 모델의 '주장'일 뿐이다. 모델이 존재하지 않는 문서 번호를 지어낼 수도 있다. 그래서 두 번째 방어는 독립적인 검증 계층이다. 답변 생성과 사실 확인을 분리하는 구조다.

전형적인 패턴은 다음과 같다.

1. 1단계: 모델이 근거 문서를 인용하며 답변을 생성한다.
2. 2단계: 검증기가 인용된 문서 번호가 실제로 존재하는지, 인용 내용이 문서와 일치하는지 확인한다.
3. 불일치가 있으면 답변을 폐기하고 다시 생성하거나, 사람에게 전달한다.

```python
def verify_against_sources(answer: str, retrieved_docs: dict) -> dict:
    cited = CITATION_PATTERN.findall(answer)
    problems = []
    for tag in cited:
        doc_id = tag.replace("[출처:", "").replace("]", "").strip()
        if doc_id not in retrieved_docs:
            problems.append("인용된 문서가 검색 결과에 없음: " + doc_id)
    return {"ok": len(problems) == 0, "problems": problems}

docs = {"doc-101": "환불 정책...", "doc-102": "배송 정책..."}
result = verify_against_sources(
    "환불은 30일 이내에 가능합니다. [출처: doc-999]", docs
)
print(result)
# {'ok': False, 'problems': ['인용된 문서가 검색 결과에 없음: doc-999']}
```

검증 계층의 핵심은 '모델이 아닌 코드가 최종 판정을 내린다'는 점이다. 정규식과 딕셔너리 조회는 할루시네이션을 일으키지 않는다. 불확실한 주체(모델)의 출력을 확실한 주체(코드)가 검사하는 구조, 이것이 검증 계층의 본질이다.

조금 더 나아가면 인용 내용과 문서 본문의 일치 여부까지 검사할 수 있다. 인용된 문장 조각이 실제 문서에 포함되어 있는지 문자열 수준에서 대조하는 방식이다. 완벽하지는 않지만, 문서 번호를 맞게 지어내는 수준의 속임수는 걸러낼 수 있다.

## 26.5 방어 3: 불확실성을 그대로 전달하라

세 번째 방어는 출력 형식의 문제다. 모델이 "확실하지 않다"고 말할 수 있게 만들어야 한다. 많은 사고는 모델이 모르는 것을 아는 척하면서 시작된다.

실무에서 쓰는 방법은 출력에 신뢰도 필드를 포함시키는 것이다.

```python
import json

RESPONSE_SCHEMA_HINT = """
답변은 다음 JSON 형식으로만 출력하세요.
{
  "answer": "사용자에게 보여줄 답변",
  "confidence": "high, medium, low 중 하나",
  "caveats": "확실하지 않은 점이나 확인이 필요한 사항을 적으세요. 없으면 빈 문자열."
}
규칙: 근거가 부족하면 confidence를 low로 표시하고, answer의 첫 문장은
"확실하지 않지만,"으로 시작하세요. 모르면 모른다고 답하세요.
"""

def handle_response(raw_json: str) -> str:
    data = json.loads(raw_json)
    if data.get("confidence") == "low":
        return (
            "이 질문에 대해서는 확실한 답을 드리기 어렵습니다. "
            "담당 부서에 확인 후 안내드리겠습니다. "
            "(메모: " + data.get("caveats", "") + ")"
        )
    return data["answer"]
```

confidence가 low인 답변을 그대로 보여주지 않고 별도 경로로 보내는 것이 포인트다. 고객 응대라면 상담원에게 넘기고, 사내 도구라면 "추가 확인 필요" 배지를 붙인다. 불확실성을 숨기지 않고 시스템이 받아들이게 만드는 설계다.

이 방식을 쓸 때 주의할 점이 있다. 모델에게 무조건 confidence를 낮게 잡으라고 압박하면, 맞는 답까지 "확실하지 않다"고만 말하는 쓸모없는 모델이 된다. 신뢰도 기준은 근거 문서의 충분함과 직접 연결되어야 한다. "근거 문서 2건 이상에서 동일한 내용이 확인되면 high" 같은 식의 구체적 기준을 프롬프트에 적어 주는 것이 좋다.

신뢰도를 시스템 내부에서만 쓰지 않고 사용자에게 직접 보여주는 방법도 있다. 답변 옆에 "근거 확인됨", "추가 확인 필요" 같은 배지를 붙이는 방식이다. 사용자는 배지를 보고 이 답변을 얼마나 믿고 행동에 옮길지 판단한다. 불확실성을 숨기지 않고 UI까지 끌어올리는 것이, 허위정보 대응의 완성형이다.

## 26.6 자주 하는 실수 세 가지

첫째, 시스템 프롬프트에 "절대 틀리면 안 된다"고 적는 것이다. 모델은 이런 추상적 명령을 지키지 못한다. "틀리면 안 된다" 대신 "근거 없으면 모른다고 답하라"처럼 행동으로 번역된 지시를 써야 한다.

둘째, 검증 계층을 같은 모델에게 맡기는 것이다. "네 답이 맞는지 다시 확인해봐"라고 하면 모델은 대개 "네, 맞습니다"라고 답한다. 검증은 반드시 모델과 독립된 코드나 다른 근거로 수행해야 한다.

셋째, 출처 표기를 장식으로 취급하는 것이다. 답변 아래에 참고 문서를 나열하는 것만으로는 부족하다. 어떤 주장이 어떤 출처에서 왔는지 문장 단위로 연결되어야 검증이 가능하다.

## 26.7 허위정보율을 어떻게 측정할 것인가

방어를 쌓았으면 효과를 측정해야 한다. "우리 시스템의 답변이 얼마나 믿을 만한가"를 숫자로 관리하지 않으면, 방어가 작동하는지 알 수 없다.

방법 1: 샘플링 평가다. 일정 기간의 답변 중 N건을 무작위로 뽑아, 사람이 근거 문서와 대조해 판정한다. 지표는 '근거 일치율'이다. 인용된 근거가 실제 문서를 뒷받침하는 답변의 비율이다. 주 1회, 50건 정도만 봐도 추세를 파악할 수 있다. 사람을 쓰는 평가라 비용이 들지만, 자동 검사로 잡히지 않는 미묘한 왜곡(근거는 맞는데 해석이 틀린 경우)을 잡는 유일한 방법이다.

방법 2: 자동 검사 지표를 본다. 26.4절의 검증 계층에서 차단된 비율, 26.3절의 출처 누락 차단 건수를 추적한다. 차단율이 갑자기 오르면 두 가지 가능성이 있다. 공격 시도가 늘었거나, 모델이나 검색의 품질이 떨어졌거나. 어느 쪽이든 조사해야 할 신호다.

방법 3: confidence 분포를 본다. 26.5절의 신뢰도 필드를 쓰는 시스템이라면, low 비율의 추이를 관리한다. low가 늘어나는데도 사용자 불만이 없다는 것은 폴백 경로가 잘 동작한다는 뜻이다. 반대로 low가 줄었는데 오답 신고가 늘면, 신뢰도 기준이 느슨해진 것이다.

```python
# 주간 리포트용 간단 집계 예시
def weekly_report(logs: list) -> dict:
    total = len(logs)
    blocked = sum(1 for l in logs if l["verdict"] == "blocked")
    low_conf = sum(1 for l in logs if l.get("confidence") == "low")
    return {
        "total": total,
        "blocked_rate": round(blocked / total, 3) if total else 0,
        "low_conf_rate": round(low_conf / total, 3) if total else 0,
    }

# 활용: 전주 대비 blocked_rate가 2배 이상이면 알림
def check_regression(this_week: dict, last_week: dict) -> bool:
    if last_week["blocked_rate"] == 0:
        return this_week["blocked_rate"] > 0.05
    return this_week["blocked_rate"] >= last_week["blocked_rate"] * 2
```

측정의 목적은 완벽한 숫자를 얻는 것이 아니라 변화의 방향을 읽는 것이다. 지표가 나빠지는 방향으로 움직이면 방어 설정을 손본다. 보안은 한 번 세우고 끝나는 것이 아니라, 측정하고 조정하는 반복이다. 이 원칙은 31장의 가드레일 운영에서도 다시 나온다.

## 26.8 실습: 출처 없는 답변을 차단하는 후처리 함수

이번 장의 실습은 26.3절의 후처리 함수를 직접 확장해 보는 것이다. 로컬에서 안전하게 따라 할 수 있는 방어 실습이다.

목표: 출처 표기가 없는 답변을 차단하고, 출처는 있지만 형식이 어긋난 답변은 교정하는 후처리 파이프라인을 만든다.

1. 새 파이썬 파일을 만들고 26.3절의 require_citation 함수와 26.4절의 verify_against_sources 함수를 복사한다.
2. 다음 기능을 추가한다.
   - 허용된 문서 번호 목록(예: ["doc-101", "doc-102"])을 받아, 목록에 없는 문서를 인용한 답변은 차단한다.
   - 출처 표기는 있지만 형식이 틀린 경우(예: [출처:doc-101]처럼 콜론 뒤 공백이 없는 경우)도 인식하도록 정규식을 개선한다.
   - 차단된 답변의 수와 사유를 로그 파일에 기록한다.
3. 테스트 케이스를 5개 이상 만들어 실행한다. 예: 출처 없음, 올바른 출처, 없는 문서 인용, 형식 오류, 출처가 여러 개인 경우.
4. 모든 테스트를 통과하면 완성이다.
5. 완성된 후처리 함수를 간단한 대화 루프에 붙여 본다. 표준 입력으로 답변 문장을 넣으면, 출처가 있는 것은 통과하고 없는 것은 차단 메시지로 바뀌는 것을 눈으로 확인한다. 코드가 정책을 강제한다는 것을 체감하는 것이 이 실습의 마지막 단계다.

이 실습을 마치면 '모델의 출력을 그대로 믿지 않고 코드로 한 번 더 거르는' 감각이 생긴다. 이 감각이 이 책의 Part 3 전체를 관통하는 기본기다.

## 26.9 정리

- LLM07 허위정보는 OWASP LLM Top 10 2026년판에서 9위에서 7위로 상승한 위협이다.
- 모델의 출력은 '정확한 문장'이 아니라 '정확해 보이는 문장'이다. 의사결정에 쓰이는 순간 보안 문제가 된다.
- 방어는 세 겹으로 쌓는다. 출처 표기 강제, 독립적인 검증 계층, 불확실성의 정직한 전달.
- 공통 원칙은 하나다. 모델의 출력을 최종 결정으로 취급하지 말고, 검증 가능한 형태로 만들어라.
- 측정이 없으면 방어가 작동하는지 알 수 없다. 차단율과 confidence 분포를 추적하라.

이 책에서 다루는 공격 기법은 모두 학습·방어 목적이며, 허가되지 않은 시스템에 대한 공격 시도는 절대 하지 말 것.
